Docker

Dockerfile
•
Un Dockerfile è un documento di testo che contiene tutti i comandi che un 
utente potrebbe eseguire da riga di comando per assemblare un’immagine
•
Contiene una sequenza di istruzioni eseguite in ordine
•
Permette di automatizzare e standardizzare la creazione dell’ambiente
•
Supporto la portabilità tra sistemi

Istruzioni principali
•
FROM – immagine di base
•
COPY / ADD – copia dei file
•
RUN – esecuzione di comandi durante la build
•
EXPOSE – porte esposte
•
CMD / ENTRYPOINT – comando di avvio del container

COPY copia file SOLO dal build 
context (la directory del docker build)
Con docker build, Docker costruisce una 
nuova immagine a layer:
layer base (FROM ubuntu)
layer RUN (es: apt install)
layer COPY (client-bin.c o server-bin.c)
layer RUN (compilazione)
Quando parte il container:
- prende tutti i layer immagine
- li monta in sola lettura
- aggiunge writable layer del container
COPY in Dockerfile diverso da
docker cp file container:/path
Che agisce nel container
RUN e COPY creano layer IMMUTABILI 
(build-time) 
CMD non crea layer (runtime)


Caching layer e invalidazione
•
Quando Docker esegue un build, ogni istruzione del Dockerfile produce un 
layer immutabile

Cosa viene messo in cache?
•
FROM ubuntu → layer base
•
RUN apt install → layer con tutti i pacchetti già installati
•
COPY client-bin.c . → layer con il file
•
RUN gcc … → layer con il binario compilato

Se una istruzione NON cambia, Docker riusa il layer precedente

Docker NON ricostruisce TUTTA l’immagine, SOLO ciò che viene dopo il primo 
layer differente.

CPU limits
•
Il kernel Linux assegna tempo CPU secondo una quota configurata.
•
Due tipi di limiti
• CPU share / quota (quanto tempo CPU puoi usare)
– --cpus=N
– --cpu-quota + --cpu-period
– Il container può usare al massimo N core-equivalenti di tempo CPU, distribuiti 
su tutti i core disponibili.
– cpu-period = durata della finestra di controllo in cui il kernel misura il tempo 
CPU, default è --cpu-period = 100000 µs (100 ms)
– cpu-period ∈[1000 µs … 1,000,000 µs], quindi min 1 ms, max 1 sec
• CPU affinity (su quali core puoi girare)
– --cpuset-cpus="1,3“
– Vincola il container a specifici core logici della macchina.

Memory limits
•
Docker usa i cgroups memory per limitare:
• memoria fisica (RAM)
• page cache
• memory + swap
•
Il limite è hard: se il container supera la memoria assegnata → OOM.
•
Esempio
• docker run --memory=512m myapp
• Il container può usare al massimo 512 MB di RAM (fisica + page cache).
• docker run --memory=512m --memory-reservation=256m myapp
– Il kernel prova a tenere sotto la reservation, ma può superarla finché c’è RAM
• docker run --memory=256m --memory-swap=512m myapp
– Può usare 256 MB RAM + 256 MB swap.
• --oom-kill-disable (sconsigliato)

# SERVIZIO A: Crea il file
creatore:
image: alpine
container_name: volume_creatore
volumes:
# Monta il volume 'dati_persistenti' nella cartella /data del container
- dati_persistenti:/data
# Comando: Crea un file chiamato 'test.txt' e scrive l'ora attuale al suo interno
command: [“sh”, “-c”, "echo 'Creato il file' > /data/test.txt && echo 'File creato! esco’”]
# SERVIZIO B: Legge il file (da lanciare separatamente)
lettore:
image: alpine
container_name: volume_lettore
volumes:
# Monta lo stesso volume 'dati_persistenti' nella cartella /data
- dati_persistenti:/data
# Comando: Legge il contenuto del file 'test.txt'
command: cat /data/test.txt
# DICHIARAZIONE DEL VOLUME NOMINATO
volumes:
dati_persistenti:
driver: local # Opzione predefinita per l'archiviazione locale

Prova volume
# 1. Avvia il container 'creatore'.
#    Il volume 'dati_perso' viene creato se non esiste.
docker compose up creatore
# 2. Rimuovi il container 'creatore'. Questo simula la perdita del container.
#    ATTENZIONE: Il volume DATI_PERSO NON viene rimosso!
docker rm volume_creatore
# Avvia il container 'lettore' e cerca di leggere il file creato nel Passo A.
docker compose up lettore
docker compose down -v
